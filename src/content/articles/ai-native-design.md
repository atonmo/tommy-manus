## Lead · 这是一次什么样的探索？

> 这是一次设计侧主动发起的内部探索。目标不是做一个「能画界面 Demo 的 AI」，而是把团队沉淀的规范、组件、经验与交付流程，整理成 AI 可执行的 Skill 与工作流，让设计师真的能用 AI 把日常设计工作做得更快、更稳、更接近生产。

它要回答的问题很具体：当设计师已经有 Figma 组件、代码组件和业务经验时，AI 能不能在约束内生成可运行结果，并进入真实业务，而不是停留在「看起来像」。

整个探索过程始于2025年年底，AI也在突飞猛进的发展，有时会觉得今天学的知识，明天就有可能落后。在这段时间里从边摸索边实践中逐渐明确了未来要走的方向路线。

## Initial Stage · 初期阶段

最开始，设计团队内部认为要想让AI能做出符合专业要求的设计方案，首先得让AI能读懂产品PRD。因为，只有像设计师一样对产品的需求背景了解了，再结合已有的设计资产，才能让AI做出满足产品需求，业务目标和设计规范的设计方案。

让AI写一个勉强能用的Skill不难，但现实是另一回事。业务场景是复杂的，每个产品的思路，经验知识也都千差万别。产品给到设计师的需求文档也是有很多的思路和结构差异，很多业务逻辑，产品资料是分散的，甚至有些经验更多存在于人与人的口头对齐中。要想让AI能读懂产品的PRD并且能准确的抓住业务和产品目标这一步就要首先解决。通过不断尝试和调整，自己总结了一套能写出好用Skill的准则：

## Advanced Stage · 进阶阶段

初期阶段的尝试是有效果的，设计工作也得到了 AI 的有效助力。但这些都只是单点的改进，如何能让 AI 真正成为生产力工具且影响整个设计工作流还亟待解决。让 Design Team 进化为 AI-Native Design Team 是当下的命题。同时在长期业务设计里，团队已经沉淀了大量资产：设计规范、组件库、页面原则、项目案例，以及和研发对齐过的 Token 与交付习惯。这些东西对新人、跨项目协作、甚至对 AI 都很有价值，要让这些资产与 AI 结合，形成一套更有驱动性和自进化性的原生能力。

随着设计师深入用 AI 一段时间后，发现了一些常见的问题：

1. 生成结果不符合设计规范，视觉和结构都像「通用 AI 味」。
2. 产出停在 Demo，研发仍要整体重写，提效几乎为零。
3. 产品和设计同学无法深入使用——因为门槛高、结果不可控、不敢进入业务仓。

> **进阶目标：AI 生成页面 → 符合设计规范 → 能进入真实业务**

这不是「写一个更好的 Skill」，而是要把设计工作本身，重新设计成一套可被 AI 执行、也可被验收的生产系统。

从能生成，到能约束，再到能进生产

## Prep · 底座准备

动手搭 AI工作流之前，我们先补齐了四块底座。没有它们，AI 只能在空地上幻觉；有了它们，AI 才有机会在「贴合业务的设计工程」里工作。

### Figma 组件库 · DESIGN

Token、状态、使用规范结构化，成为生成边界。

### 代码组件库 · CODE

Web / iOS / Android + Token 映射，保证输出不是凭空 JSX。

### GitLab 仓库 · REPO

Skill、Starter、发布与 Handoff 资产版本化。

### 三端 Starter · RUNTIME

依赖、字体、主题、组件已挂载，开箱可编译。

> **核心理念：给 AI 一个已配好的工程，而不是让它从零搭项目。**

解决问题：不用底座时，AI 会卡在工程配置、依赖混乱和编译失败；有底座后，AI 专注生成页面，人专注验收与判断。底座准备，本质上也是设计工作。

## 01 · 第一个版本：生成 Demo，看起来很快

最早的路线很直觉：既然有 Figma 组件，就让 AI 关联组件语义，直接生成可交互页面。

[[embed:demo-flow]]

我们先用 Flutter + Skill 跑通了一遍，证明「符合规范的生成」有机会成立。

这个版本的优点很明显——上手快、依赖少、演示效果好。但它很快暴露出一个致命问题：

**研发仍要构建页面，Demo 只是换了一种表达方式，并没有进入生产流程。**

行业侧的Bolt.new、Lovable等也在验证同一方向：只有生成可运行的真实代码，AI 才有机会进入业务。我们因此放弃「好看的 Demo 路线」，转向路线 B——生成三端真实可运行代码。

[[embed:route-shift]]

## 02 · 第二个版本：真代码能出，但 Skill 把 AI 带迷路

转向真实代码后，新问题立刻出现。早期 Skill 结构过度索引，入口文件指向一堆必读文档，组件规范、工程说明、页面风格各占一份，AI 的行为变成：

读 Skill → 跳文件 A → 回来 → 跳文件 B → 执行。这样造成了很大的问题是：读了一半就开始干活，漏掉关键红线。

[[img:mistake]]

结果是：有时能编译，有时视觉漂移，多轮改 UI 后规范被「挤出」上下文，设计师的体感很差。明确能感受到不是 AI 不会画图，而是规则系统本身不适合被 AI 执行。

> **问题洞察：**设计师真实需求很少是单点的**。** 设计师不会只提出「Button 的圆角要求8px」，而会问「按我们的规范，把这个活动页做成可上线的三端页面」。这需要规范、组件、素材、工程约束一起生效；散乱的多文件 Skill 扛不住这种综合任务。

这个版本让我意识到：设计提效的关键，不只是更强的模型，而是把「设计师如何保证质量」翻译成 AI 不会迷路的注意力结构。

## 03 · 第三个版本：单入口 Skill + 硬规则前置

我们重构了 Skill，以 **web-design** 为例：单一 `SKILL.md` 入口，按注意力分层；组件 JSON、知识库、素材库按需读取。

#### L1 · 入口 + 硬规则

红线前置，注意力最高，反复改 UI 也不轻易丢。

#### L2 · 基础设计系统

Token 与组件约定，锁住生成边界。

#### L3 · 设计判断

去 AI 味、信息层级、品牌感——把设计师的品味写成可执行标准。

#### L4 · 执行 + 验收

预览、验收、Handoff，把「做完」定义清楚。

重构前后差异很具体：

- **文件结构**：8+ 互相引用 → 1 主文件 + 按需加载
- **AI Read 次数**：5–8 次易迷路 → 0–2 次按需
- **规则遗漏**：显著下降；多轮改 UI 仍守规范

> **阶段洞察：Skill 不是越复杂越好。简洁明了的主流程，关键红线不能漏，细节懒加载。**

这一步之后，AI 才真正开始「改进设计工作」：设计师把判断写进系统，而不是每次对话重新教一遍。


## 04 · 第四个版本：从单点生成到交付代码生产闭环（改进中）

Skill 跑通后，下一步是把结果交给研发。Web 端基本可以，但 App 端较复杂：模拟器、Gradle、Mock、多语言、路由等等，直接改真实业务仓风险过高，产品和设计也无法判断代码风险。

于是我们补上工作流收口：产品/设计接需求 → AI 在 Starter 中生成 → 本地预览编译 → 视觉验收 → 产出交付包 → 研发集成业务仓。遇到的问题再反哺 Skill / 组件 / Starter。
补充了如下几个重要 Skill，尽量确保交付的代码质量符合工程仓要求。

#### INTEGRATION.md

集成说明，降低研发接手摩擦。

#### DATA_CONTRACT.md

数据契约，把 Mock 与真实 API 对齐。

#### QA_CHECKLIST.md

验收清单，跨角色交付可审计。


> **到这里，链路才算从「能生成一个页面」走到「能进入真实业务流程」。**

## Design Reflection · 项目回顾

回顾整个 AI-Native 项目，它让我对「用 AI 改进设计」有了更具体的理解。开始时很容易把 AI 想象成：给一句需求，就能吐出合格界面。真正做下来会发现——要让 AI 成为可用的设计生产工具，需要大量人为设计的结构与约束。
它不是简单地把模型接上组件库，也不是让模型自由发挥审美，而是需要围绕设计任务建立一套机制：
模型提供生成力；真正让它改进设计工作的，是规范、Starter、Skill、Handoff 与人的判断共同构成的那套工作系统。设计师主动设计 AI 的工作方式时，AI 才有机会从「会画图的工具」，变成「能进入生产的设计搭档」。
